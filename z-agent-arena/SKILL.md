# 并行竞技场（z-agent-arena）

## 1. 核心指令

用户输入为「需求」。流程固定三步：并行竞演 → 横向对比 → 合成交付。三步完成后一次性交付，禁止跳过对比直接给单一结果，禁止只宣布赢家而不合成。

## 2. 并行竞演

1. **数量**：子代理数量 N 由用户在提出需求时指定；未指定取 3。N 小于 3 按 3、大于 7 按 7 执行，并向用户说明修正后的取值。
2. **主线程参赛**：主线程与 N 个子代理同台竞技，共 N+1 路结果。派发前，主线程先按需求独立完成一遍执行——读文件、查信息、落实指代，产出自己的参赛结果。
3. **如实打包**：子代理与主对话完全隔离，只看得到派发的需求包。需求包 = 需求原文 + 主线程执行中实际引入的资源（如读过的文件与关键内容、查证的事实、对话带入的约束与背景）。不预定义资源类型，用到什么打包什么；执行中发现资源不足时，先向用户追问。N 个子代理收到的需求包完全一致。
4. **一致性边界**：需求包只打包资源，不打包主线程的解题思路、分析判断与参赛结果——主线程已完整解过题，思路一旦入包，N 路子代理的竞演就退化为对主线程思路的 N 次复制。
5. **并行派发**：使用环境的并行子代理机制（如 task 工具），N 个派发调用放在同一批工具调用中同时发出，不串行。需求包是公共起点而非资源上限，子代理可自行补充查阅。
6. **异常处理**：任何一路结果失败或为空（含主线程）时如实标注，不虚构补位；有效结果不足 2 份时终止流程，向用户报告原因。

## 3. 横向对比

N+1 路结果全部返回后，逐一评估：

- 对比维度按需求类型确定（如正确性、完整性、可执行性、表达质量、成本），同一轮对比内统一，不因结果调整。
- 每个结果列出明确的优势与缺陷，附具体依据：引用结果原文，或指认缺失与错误之处。
- 各结果无实质差异时如实说明，不制造差异。
- 主线程结果同一标准参评，对比与合成不因出处偏袒。

**输出**：对比表（结果编号 | 优势 | 缺陷 | 结论）。

## 4. 合成

以对比结论为依据，取精华、去糟粕：

- **取**：各结果中经对比确认的可验证、可落地的部分。
- **去**：对比中已指认的缺陷、错误与冗余。
- **合**：合并重叠内容，消解冲突；冲突处以对比中更优的一方为准，并注明取舍理由。合成结果必须自洽，可直接使用。

若某结果整体显著优于其余，允许以其为主体，但须吸收其余结果的有效增量。

## 5. 交付

依次输出：任务执行简报 → 对比表 → 综合最优结果 → 简要取舍说明（取自哪些结果、剔除了什么）。结果形态跟随需求类型（代码、方案、文档、答案等），不套固定模板。

**任务执行简报**：置于交付开头，以**散文格调和段落形式**简要说明以下点：

- 对任务的理解（需求实质、目标与关键约束）。
- 各结果的特点与结论（每个一句概括）。
- 各结果的共识（多数结果一致的要点）。
- 最终判断和结论。
