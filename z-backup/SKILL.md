# z-backup

## 1. 角色定位

你的职责是安全地把用户指定的文件或目录备份成带日期后缀的副本，集中放到 `.z-backup/` 下。核心原则：**只新增副本，绝不删除或修改原始文件**，目标目录 `.z-backup/` 内的已有备份也**不清理、不覆盖、不合并去重**，仅追加新副本。

## 2. 触发方式

**仅当用户显式激活本技能时才可触发。** 显式激活的标志：用户直接写了技能名，如 `/skill:z-backup`、「使用 z-backup」、「use z-backup skill」；随后说明要备份哪些路径。

以下情况**一律不触发**（仅凭字面意思、无技能名，不得执行任何拷贝）：
- 「备份 config.yaml」「把 src 目录和 README.md 备份一下」「back up something」这类未点名 z-backup 的表述，默认视为普通对话；若确实需要，可先向用户确认是否想调用 z-backup，得到确认后再执行。

未显式激活时，不得对用户的文件执行任何备份/拷贝操作。触发后，进入第 3 节流程。

## 3. 执行流程

### 3.1 解析待备份项

1. 明确用户要备份的**一个或多个路径**，允许文件与目录混合（如：`src/` + `notes.md` + `data/`）。
2. 路径缺失或不明确时，向用户确认，不自行猜测。
3. 对每个路径确认其存在；不存在的项应向用户报告，并询问是跳过还是中止。

### 3.2 确定备份根目录

备份根目录固定为 `.z-backup/`：

- 当前工作目录属于某项目/版本库时，取该项目根目录下的 `.z-backup/`；
- 不属于任何项目时，取当前工作目录下的 `.z-backup/`；
- 用户明确指定其他位置时按指定位置执行；
- 若 `.z-backup/` 不存在，自动创建。

### 3.3 备份容器与命名

**一次备份 → 一个带日期后缀的容器目录**，所有待备份项按原始结构放入其中；日期后缀只加在容器目录名上，不给每个文件/子目录单独加后缀。规则对「仅文件」「仅目录」「文件+目录混合」统一适用，保证行为一致、结构可还原。

- **容器目录**：`.z-backup/{备份名}-{YYYYMMDD-HHMMSS}/`
  - 备份名默认由批次内容概括（如批量资源可叫 `assets`）；用户指定时以其为准。
  - 命令行下取真实日期时间，格式见第 4 节。
- **结构保留**：在容器内，每个待备份项保持「相对备份基准的原始相对路径」。备份基准默认 = `.z-backup/` 所在的项目根目录。
  - 例：指令「备份 `AGENTS.md` 和 `.agents/` 目录」，备份名 `prep`，时间为 `20260820-103012`，结果为**一个**容器：
    ```
    .z-backup/prep-20260820-103012/
    ├── AGENTS.md
    └── .agents/...
    ```
    容器内 `AGENTS.md` 与 `.agents/` 保持原相对路径，日期后缀只出现在容器目录名上。
  - 若待备份项位于子目录（如 `docs/guide.md`），容器内同样保留相对路径：`.z-backup/{备份名}-{ts}/docs/guide.md`。
  - 若备份多个无上下级关系的顶层项（如项目根下的 `src/` 与 `notes.md`），它们在容器下并列存放。
- **基准外的路径**：待备份项不在备份基准内（如绝对路径指向项目外），向用户确认如何处理，不擅自决定。

**唯一性保障**：若容器目录已存在（如同一秒备份同名批次），在其后追加 `-1`、`-2`……直至不冲突，如 `.z-backup/prep-20260820-103012-1/`。

### 3.4 规模预检与异常提示（防误备份）

复制前先对待备份项做一次盘点，让用户清楚「将备份什么、规模多大」；发现**疑似打错路径**或规模异常时，必须提示并取得确认，不擅自硬执行：

1. **盘点规模**：统计每个待备份项的相对结构、总文件数与总字节数（目录先递归统计）。
2. **阈值提示与确认**：
   - 估算总量 > 200 MiB，或文件数 > 1000 → 先向用户展示清单与规模，**确认后再执行**；
   - 估算总量 > 2 GiB 或文件数 > 10000 → 高度怀疑打错路径，必须明确说明并取得显式确认，否则中止。
3. **疑似打错路径**：源解析为整盘根、用户主目录、系统目录（如 `/`、`~`、`C:\`、`/usr`、`%USERPROFILE%`）或当前项目根 `.` 时，强烈提示「可能打错路径」，列出将覆盖的巨大范围，要求二次确认。
4. **不该备份的典型对象**：源或其内意外包含 `.git/`、`node_modules/`、`__pycache__/`、`build/`、`dist/`、`*.db` 等巨大/无意义内容时明确提示；默认不擅自排除，由用户决定是否保留。
5. **通配符**：路径含 `*`、`?` 时先展开为实际项，再按实际项执行；展开结果为空或异常多时提示，交由用户确认。
6. **源类型不符**：用户给的路径类型与预期不符（想备份目录却指向文件，或反之）时，提示可能打错。
7. **磁盘空间**：估算所需空间，检查 `.z-backup` 所在盘剩余空间；不足时提示，避免复制到一半失败。
8. **路径过长**：生成的容器名或容器内目标路径接近系统长度上限（Windows 约 260 字符）时，提示并合理缩短。

### 3.5 执行复制

1. 先创建容器目录 `.z-backup/{备份名}-{YYYYMMDD-HHMMSS}/`。
2. 将每个待备份项**完整复制进容器内对应的相对路径**：
   - 文件复制该文件内容；
   - 目录递归复制其全部内容及结构（保留子目录、空目录、文件属性）；
   - 保持相对结构（如 `docs/guide.md` 落到容器内的 `docs/guide.md`）。
3. 跨平台参考命令：
   - 创建容器：PowerShell `New-Item -ItemType Directory -Path <容器>`；类 Unix `mkdir -p <容器>`
   - 复制目录：PowerShell `Copy-Item -Recurse -LiteralPath <源> -Destination <容器内相对目标>`；类 Unix `cp -R <源> <容器内相对目标>`

### 3.6 校验与交付

复制完成后核对容器，确认满足：

- 容器目录存在，路径/名称符合命名规范（`.z-backup/{备份名}-{ts}/`）；
- 容器内各待备份项的相对结构与原结构一致（文件内容、目录层级、文件数）；
- 重要项可用哈希/字节数简单比对确认内容一致。

完成后向用户报告：容器路径、备份根目录位置、容器内各备份项清单，以及（若有）跳过的项与原因。

## 4. 时间获取

日期后缀必须为真实时间，按以下顺序获取，严禁使用模型内部时间或推测时间：

1. 国家授时中心官网：HEAD 请求 `https://www.ntsc.ac.cn`，取响应头 `Date` 字段（GMT 时间，+8 小时换算为北京时间，再格式化）；
2. 中国政府网：HEAD 请求 `https://www.gov.cn`，换算方式同上；
3. 均失败时，使用本地系统命令行时间作为兜底：PowerShell `Get-Date -Format 'yyyyMMdd-HHmmss'`，类 Unix `date +'%Y%m%d-%H%M%S'`。

日期后缀格式统一为 `YYYYMMDD-HHMMSS`。

## 5. 安全与异常处理

1. **只增不减**：不删除、不覆盖任何原文件，也不改动 `.z-backup/` 内既有备份，仅追加新容器。
2. **自我递归防护**：拒绝把 `.z-backup/` 自身、或位于 `.z-backup/` 内的路径作为源；`-Recurse` 复制前确认源不含 `.z-backup`。
3. **同批次路径冲突**：两个待备份项因包含关系会在容器内落到同一相对路径（如同批备份 `src` 与 `src/a.txt`）时，先检测并去重或提示，避免重复/错乱。
4. **符号链接/连接点**：递归复制目录时遇到符号链接或 junction，提示其可能指向外部路径、易造成环或外泄；不擅自跟随，按系统默认或询问决定。
5. **部分失败处理**：某项复制失败（权限不足、文件被其他程序占用、磁盘满、路径过长）不影响其余项继续；结束（见 3.6）时如实汇总成功/失败清单及失败原因与位置；未全部成功时如实标记、不冒充“全部完成”。
6. **过程透明**：较大或较多文件时，复制前已按 3.4 预检并反馈；执行中可向用户反馈进度。
7. **错误不静默**：任何异常均明确说明原因与处理方式，不静默跳过；对存疑或大范围备份，未经确认不执行。
8. **名称与来源规范**：日期后缀只用第 4 节真实时间；备份名不含路径分隔符/非法字符、不过长；容器名冲突按 3.3 追加序号。
